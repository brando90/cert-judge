# EXP44 (dir 22) — Pooled Held-Out Power Analysis, Noise Ceiling, and a Label-Protocol Audit (CORRECTED by stage-1 verification)

**TLDR:** The planned pooled analysis (n 8→20/32) still showed a flat null — and chasing an impossible-geometry contradiction surfaced the real story, in two stages. **Stage 1 (this report's first version) blamed a data-integrity failure in `results_exp16_final_robust_r9_median/detail_rows.csv`; independent stage-1 QA verification REFUTED that claim** — `detail_rows.csv` reproduces every published `judge_rows.csv` calibration correlation to machine precision (all 8 judges × 3 label sets, |Δ| < 1e-12) when joined with the label files exp16 actually used (`experiments/04_veribench_validation/data/ethan_human_scores_*.tsv`). **The true mechanism is labeling-protocol drift**: the calibration labels come from an earlier annotation campaign (`old_prompt` lineage) that is nearly uncorrelated (ρ ≈ 0.13, n=63) with the revised-protocol campaign (participant pool + expert strict/lenient sets) — the same annotator agrees with the pool at ρ = 0.90 under the revised protocol but with their own earlier labels at only ρ ≈ 0.18. The label-side news is good and verified: the five-rater pool is reliable (Spearman–Brown ceiling ≈ 0.87) and within-campaign stable. Recommendation unchanged in effect — do not submit a negative-transfer claim — but the fix is **label-protocol re-anchoring (one protocol end-to-end), not judge re-scoring**: the score files were never broken.

## Finding C (CORRECTED 2026-07-21) — the "internal inconsistency" was a wrong-label join; the score files are consistent

**Original claim (REFUTED):** `detail_rows.csv` cannot reproduce the published `judge_rows.csv` calibration correlations in its own directory (e.g. Codex P1 +0.466 published vs +0.022 recomputed; BAD_STRINGY +0.435 vs −0.304), therefore the file is a corrupt/stray regeneration and every downstream number is void.

**Stage-1 verification (independent recomputation, scipy `spearmanr`, exact-key join):** recomputing each judge's `human_spearman_r_{pass1,pass2,avg}` from `detail_rows.csv` (`human_eval_union.score_mean`) against the label files exp16's code actually loads (`ethan_human_scores_20260425.tsv`, `ethan_human_scores_ORIGINAL.tsv`, `ethan_human_scores_avg_two_passes_20260425.tsv`) reproduces the published `judge_rows.csv` values **exactly** for all 8 judges and all 3 label sets (max |Δ| < 1e-12; e.g. Codex P1 avg recomputed 0.46642224929062365 ≡ published; BAD_STRINGY 0.4348089142498352 ≡ published). The original audit had recomputed against `experiments/human_labels/expert_harsh_set_data.tsv` + `lenient_set_data.tsv` with last-occurrence-wins loading — files from a *different annotation campaign* that exp16 never used (that procedure reproduces the audit's table: P1 +0.027≈+0.022, BAD −0.305≈−0.304, random +0.278≈+0.277). Secondary evidence also dissolves: the 3-entry `repeat_scores` lists in an "r9" directory are the judge-call cache returning 3 stored repeats for LLM judges (`summary.json` records `judge_repeats=9`; editdist/random rows have exactly 9 entries) — same-run artifacts, not a stray regeneration. The exp30 corroboration (editdist `human_spearman` 0.1986746699690646 ≡ judge_rows) is consistent with all of this: *both* published files and `detail_rows.csv` describe the same, internally consistent scores.

**The true mechanism — two nearly-uncorrelated labeling campaigns:**

| comparison (exact-key join, repeat labels averaged) | Spearman | n |
|---|---:|---:|
| calibration labels (ethan avg) vs five-rater pool mean | **+0.13** | 63 |
| same annotator: revised-protocol relabel (`ethans_data_same_prompt.tsv`) vs own earlier labels (ethan avg) | **+0.18** | 63 |
| participant1: old-prompt labels vs own correct-prompt relabel | +0.19 | 63 |
| participant1 old-prompt labels vs calibration labels (ethan avg) | +0.84 | 75 |
| revised-protocol annotator relabel vs pool mean | **+0.90** | 75 |
| expert strict-pass set vs pool mean | +0.96 (0.899 under last-wins loading) | 78 |

The campaigns split cleanly: {ethan_ORIGINAL, ethan_20260425, old_prompt/participant1} form the **old-protocol cluster** (used for all calibration numbers and TI_var development); {participant1–5, expert_harsh, lenient, ethans_same_prompt} form the **revised-protocol cluster** (the held-out pool). Within-cluster agreement is high; across-cluster agreement is ≈0.1–0.2. The scored artifacts themselves did not change (`data/generated_agents/*.lean` untouched in git since 2026-04-07, before all labeling; the gold files resolve to the same `veribench` sources) — what changed is the labeling protocol/instructions. Directionally consistent with a lexical→semantic rubric shift: under old-protocol labels the lexical negative controls score *positive* (editdist +0.20, BAD_STRINGY +0.43); against the revised-protocol pool they score *negative* (editdist −0.57, BAD_STRINGY −0.46).

**Consequences:** exp43 (and exp22's Analysis A) correlated frozen TI_var — developed against the old-protocol construct — with judge alignment to the revised-protocol pool. The near-zero result is a valid computation but **cannot distinguish "TI_var fails to transfer" from "the target construct changed"** — the transfer question is OPEN, for this (verified) reason, not because of data corruption. The clean judge-level fact is reportable: judges that track the old-protocol calibration labels at up to ρ ≈ 0.47 track the revised-protocol pool at ≈0 (median −0.24 across the 14 real unique configs; best +0.42, LeanStral P1; Codex P1 −0.20, n=60 aligned items). exp42 is **not** confounded (it calibrates judge scores against pool labels only, train/test split over tasks — one protocol end-to-end); its null/negative zero-leakage transfer result stands as valid evidence. exp41/exp38 oracle bounds are pool-internal and keep their existing "not held-out evidence" label. No quarantine of `detail_rows.csv` is warranted.

How this was caught (both times): the original annotator "agrees with the pool at ρ=0.90, yet judges correlated +0.47 with one and ≈0 with the other" — that geometry seemed impossible on shared data. The resolution is that the 0.90 and the 0.47 involve *different label sets by the same annotator* (revised-protocol relabel vs old-protocol originals), which agree with each other at only ρ ≈ 0.18.

## Finding B (VERIFIED, attribution corrected) — the pool is reliable and within-campaign stable; it does NOT corroborate the calibration target

Only human-label files involved; unaffected by Finding C either way.

- Five-rater pool: 78 items, 343 labels, ~4.4 raters/item; mean pairwise inter-rater Spearman 0.42 (weighted; range 0.05–0.87 — participant5 is the outlier, 0.22–0.46 vs everyone).
- Spearman–Brown reliability of the pool mean: 0.76 (K_eff=4.4), 0.78 (K=5) → **achievable judge-vs-pool-mean ceiling ≈ 0.87–0.88**. Label noise does NOT explain a null transfer result.
- Leave-one-rater-out human bar: mean 0.57 (0.29–0.82 per rater).
- Within-campaign anchor: the revised-protocol expert strict-pass set matches the pool mean at ρ = 0.96 (n=78, repeat labels averaged; 0.899 under last-occurrence loading, the number quoted in the first version of this report); the same annotator's revised-protocol relabel matches at ρ = 0.90 (n=75); the lenient set alone at ρ = 0.54.
- **Correction:** the first version called this "the calibration target is corroborated." It is not — the strict-pass and lenient sets belong to the *revised* campaign, while the calibration target is the *old-protocol* label set, which matches the pool at only ρ ≈ 0.13. The pool corroborates itself (within-protocol stability), and thereby sharpens the drift finding.

## Finding A (EXPLORATORY + CONFOUNDED — numbers valid, transfer interpretation blocked by Finding C)

Pooled frozen analysis on the (internally consistent) detail_rows scores vs pool labels: pooled 32 rows ρ=−0.124 (clustered CI [−0.71, 0.65]); unique 20 configs ρ=−0.075 [−0.55, 0.41]; real judges only (n=14) ρ=−0.218; within-family-centered ρ=−0.029, permutation p=0.87. These are valid computations of the confounded comparison described in Finding C: they measure old-protocol-built TI_var against revised-protocol alignment, and additionally were chosen post hoc after seeing per-family nulls. They should not be cited as evidence for *or against* TI_var transfer.

## Recommended decision + rationale

1. **Do not submit a negative-transfer (or positive-transfer) held-out claim.** The frozen test compared against a target whose labeling protocol differs from the calibration protocol; a two-stage audit (integrity hypothesis → refuted → protocol drift verified) is disclosed in the paper instead.
2. **The decisive step is label-protocol re-anchoring, not judge re-scoring.** The judge scores are verified consistent; what is missing is one protocol end-to-end. Either (a) re-calibrate TI_var development against revised-protocol labels on the calibration panel (requires relabeling the n=75 panel under the revised protocol, or splitting the existing pool), then run the frozen held-out test within-protocol; or (b) pre-register that the revised-protocol pool defines the construct and report judges/TI_var against it. New judge scoring is optional (only needed for r9-true repeats or new configs), not a validity requirement.
3. **Why this is interpretable either way:** the pool is reliable (ceiling 0.87) and within-campaign stable (0.90–0.96 anchors), so a within-protocol rerun lands cleanly. Positive → strong TMLR paper. Null/negative → honest measurement-lessons paper (the audit trail — including the refuted first hypothesis — is itself a contribution about artifact-level verification).
4. Repo hygiene: `detail_rows.csv` needs **no quarantine** (earlier flag withdrawn); the real hazard to document is the label-file lineage — `experiments/human_labels/` (revised protocol) vs `experiments/04_veribench_validation/data/ethan_human_scores_*` (old protocol) must never be joined as if interchangeable. exp42 stands; exp41/exp38 keep their oracle-only labels.
